How the C++ for a model is generated

The model equations come from libCellML. Everything around them (the solver, output, the driver, the build, and the code that exchanges values with other models) comes from ten Jinja2 templates. This page puts each template beside the C++ it produced for the 3D-heart CVS-ANS model (3C_ANS_3Dheart). The pipe-coupling examples come from the FV 1D test model (aortic_bif_hybrid_V1).

How it fits together

You run generation with model_type: cpp, e.g. python scripts/model_generation.py --variant 3Dheart --model-type cpp. The generator builds the CellML model from your vessel array and module configs as usual, then:

What an external variable is. The key idea is that any value that comes from outside the CellML is made a libCellML external variable. Examples are a pressure set by lifex, a boundary condition received from the 1D solver, and a delayed value. libCellML's code then asks for it through a callback, the wrapper answers from a cache, and the generated hooks and api methods keep that cache up to date.

What runs when

Every solver calls Model0d::computeRates for each right-hand-side evaluation. main0d or the lifex class calls solveOneStep once per step. The hooks are where values are exchanged with other models.

sequenceDiagram
  participant D as main0d / lifex::Circulation
  participant M as Model0d (model0d.cpp)
  participant L as libCellML code (model0d_core.c)
  participant X as coupled model (1D solver / lifex)
  D->>M: initialiseVariablesAndComputeConstants()
  M->>L: initialiseVariables, computeComputedConstants
  M->>X: hookInit (e.g. read 1D volume)
  loop every step
    D->>M: solveOneStep(dt)
    M->>X: hookStepStart (e.g. agree dt)
    loop every solver stage / CVODE call
      M->>M: hookRhsStart (delays into cache)
      M->>L: computeVariables
      M->>X: hookRhs (send port values, receive BCs into cache)
      M->>L: computeRates (reads cache via externalVariable)
    end
    M->>X: hookStepEnd (e.g. step done, read volume)
  end

For the 3D heart there are no hooks. lifex sets the pressures into the cache between steps through the api class, and solve_time_step() then calls solveOneStep.

Reading a template

A template is ordinary C++ with Jinja2 tags. Rendering replaces the tags with values from the context dict built in generator.py. Most of the template is copied through unchanged.

{% for x in xs %} … {% endfor %}repeat the block per itemone ext_cache[…] = …; line per external variable
{% set x = … %}a local name inside the template{% set CB = ', externalVariableCallback' … %}

Lines starting with # (#include, #if SUNDIALS_VERSION_MAJOR) are C preprocessor lines, not template lines. They pass through rendering unchanged and are dealt with by the C compiler.

Template beside generated code

Each example shows the relevant part of a template and the matching part of the generated file. Long excerpts are shortened where marked. Everything shown is copied from the real files.

The equations: libCellML output, before and after naming

  • libCellML writes the model equations as C with array indices only. The generator then renames every states[i], rates[i] and variables[i] in the four compute functions (initialiseVariables, computeComputedConstants, computeRates, computeVariables). It also renames the index argument of externalVariable(…).
  • This file is not rendered from a template. It is libCellML's code with the numbers swapped for names, so the compiled program is identical.
  • S_… indexes states and rates (a rate has the same index as its state); V_… indexes variables. The names are the generated Python's attribute names: var.heart_module_u_lv in Python is variables[V_heart_module_u_lv] here.
  • External variables (set from outside the CellML) appear as variables[V_x] = externalVariable(…, V_x). The wrapper answers those calls from its cache.

The index names in the header

  • The header lists every name once, with its component, variable, units and variable type in a comment. Look a name up here when reading the equations.
  • The enum sits just above libCellML's own declarations. STATE_INFO/VARIABLE_INFO (names and units as strings, used by the output code) are untouched.
  • The libCellML function signatures stay as generated. The ExternalVariable callback type exists only because this model has external variables; without them libCellML drops the callback argument, and the templates allow for that with {% if has_externals %}.

model0d.h: the Model0d class

  • Declares Model0d, the C++ class around the libCellML functions. The public part is what main0d, the lifex api class and the coupler-driven runs use: the arrays, time, set_ode_solver, initialiseVariablesAndComputeConstants, solveOneStep, output and pipes.
  • {{ dt_solver }} becomes the default step. {{ n_connections }} becomes the number of 1D-0D pipe connections (0 for the 3D-heart model).
  • {% if solver == 'CVODE' %} keeps the CVODE members; an RK4 model would not have them. {% if pipes %} adds one std::ofstream/std::ifstream member per pipe. This model has no pipes, so that block is empty.
  • Snapshot/restore save and reload the whole model state. The lifex get_volume_chamber_extrapolated uses them for trial steps.

model0d.cpp: constructor and the external-variable cache

  • The constructor allocates the libCellML arrays and zero-fills them (libCellML fills them with NaN).
  • {% for e in externals if e.initial is not none %} writes one line per external variable, seeding the cache with its starting value. For the 3D heart these are the four chamber pressures, starting from the placeholder parameters (400 and 1000 Pa) until lifex sets them.
  • {{ e.ref.name }} is the external's named index and {{ e.ref.label }} its component/variable. Every generated line that touches a model value carries such a comment.

model0d.cpp: one right-hand-side evaluation

  • Every solver calls this for each right-hand-side evaluation (CVODE through cvodeRhs; RK4 four times a step). The order matters.
  • 1. hookRhsStart: delayed values and, for FV 1D, the time message. 2. libCellML computeVariables: algebraic variables from the current states, including the values sent to coupled models. 3. hookRhs: exchange with coupled models, which writes new external values into the cache. 4. libCellML computeRates, which reads those new values.
  • {{ CB }} is , externalVariableCallback when the model has external variables, and nothing otherwise, because libCellML's signatures differ.
  • ::computeRates (with ::) is libCellML's C function; Model0d::computeRates is this wrapper.

model0d.cpp: the CVODE right-hand side

  • CVODE calls this function. It computes dtLoc, the internal step CVODE is taking: hcur on the first call of a new step, and 0 on the extra calls CVODE makes for Newton iterations and its finite-difference Jacobian.
  • The FV 1D solver weights its own update by this value, so the rule copies the previous generator exactly.
  • Only rendered for solver: CVODE ({% if solver == 'CVODE' %}).

model0d.cpp: one step (solveOneStep)

  • One output step. hookStepStart runs first (FV 1D: agree the step with the coupler), then the integration, then hookStepEnd (FV 1D: the step-done message and the 1D volume).
  • A CVODE build integrates with CVODE when ODEsolver is CVODE, and falls through to the fixed-step schemes (explEul, Heun, midpoint, RK4) otherwise. } else followed by the explicit block is how the template joins the two.
  • The explicit schemes pass 0, dt/2 or dt as dtLoc for each stage. The coupled 1D solver relies on these values.
  • After the step: recompute the algebraic variables, store delay histories (when the model has delays), and restore the requested dt.

Pipe hooks: api block → generated exchange

  • The hook bodies are not written in the template. They are C++ lines generated in Python (externals.build_named_pipe_code) from the calls of the model's api block, shown on the left, and passed in as hooks.rhs.
  • The bc_exchange call has "per": "connection", so there is one write and one read per 1D-0D connection, all writes first. Each connection sends its 0D port value (port.flow here, since the terminal receives pressure) and receives port.input, which goes into the cache with setExternal.
  • The terminal's inflow is a state (s[S_terminal_1_module_v]); the pressure it receives is a parameter-component variable (V_parameters_u_in_terminal_1).
  • if (pipesOpen) skips the exchange when main0d runs without -coupled 1. For the 3D-heart model all hooks are empty.

solver_init.j2: setting up CVODE

  • set_ode_solver sets up CVODE: a BDF solver with a dense direct linear solver. {{ n_max_steps }}, {{ dt_solver }}, {{ reltol }} and {{ abstol }} come from solver_info (MaximumNumberOfSteps, dt_solver, rtol, atol).
  • The #if SUNDIALS_VERSION_MAJOR lines are C preprocessor lines, not template lines, so they appear in the output unchanged. The C compiler picks the SUNDIALS 5, 6 or 7 calls for whichever version CMake found.
  • This template is included into model0d.cpp.j2 with {% include 'solver_init.j2' %}, and the tests also render it on its own.

pipes.j2: opening the named pipes

  • {% for p in pipes.send_pipes %} writes one open-and-check block per pipe. The pipe names come from the api block's channels, with {i} replaced by the connection number.
  • Writers open before readers, in the channel order of the api block. Opening a named pipe blocks until the other end opens it, so this order has to match the coupler's.
  • Only channels that some call uses are opened. This model has no 1D volume sum, so parent_to_zero_vol is left out; the coupler does not create it either.

io.j2: output files

  • Output files are sol0D_states.txt and sol0D_variables.txt, with a header line # 0: t[s]; 1: module/variable[units]; …. The 1D solver, loadFromFile and plotting scripts read that header, so the format is fixed.
  • This function decides which variables are written: algebraic and external ones that belong to a *_module component or to parameters.
  • {% if has_externals %} adds the EXTERNAL type, which only exists in libCellML's header when the model has external variables.

main0d.cpp.j2: the driver program

  • The driver program. On its own it runs ./main0d [-tEnd t] [-tSave t] [-outDir d] [-ODEsolver S]. Under the 1D-0D coupler it gets -coupled 1 -T0 -nCC -pipePath …, the command line the coupler has always used.
  • {{ output_dir }}, {{ default_T0 }} and the end and save times become the defaults. The end time is pre_time + sim_time from the user inputs.
  • The time loop steps at dt_solver ({{ dt_solver }}) and writes a row every dt ({{ dt_sample }}).

CMakeLists.txt.j2: the build

  • Three targets: model0d_core (libCellML's C), model0d (the C++ wrapper plus SUNDIALS) and main0d.
  • SUNDIALS is found as a CMake package first. Give -DSUNDIALS_DIR=<install prefix> if CMake doesn't find it (on this machine, ~/software/sundials-7.1.1).
  • {% for extra in extra_targets %} adds the api library (circulation_api) and the api_test_driver when a provider api is connected, as for the 3D heart.

api_provider.h.j2: the lifex Circulation class

  • The class another program calls. Here the api block says namespace: lifex, class_name: Circulation, so the result is a drop-in lifex::Circulation.
  • One declaration per entry in the api block's functions. The kind picks the signature: set → void f(const double &), get → double f() const, set_indexed → takes an iheart::Chamber, extrapolate → lifex's get_volume_chamber_extrapolated signature.
  • The comment above each declaration is the CellML variable the function reaches through the ports, and its api units.

api_provider.cpp.j2: what each method does

  • set: the value arrives in api units (mmHg), is multiplied by {{ f.factor }} (133.32 Pa per mmHg) and written to the external variable's cache slot. The chamber pressure p_lv_3D on the 3D module's port resolves through chamber_pressure_port to the CellML heart's u_lv_ext.
  • get: reads a state or variable and divides by the factor (1e-6 m³ per ml for volumes).
  • step: advances the model to the time given by set_time. Setting a pressure marks the inputs as changed, and the next advance restarts CVODE, because a jump in an input is a discontinuity for its multistep method.
  • {{ f.ref.cpp('model_.states', 'model_.variables') }} writes model_.states[S_…] or model_.variables[V_…], depending on whether the variable is a state.

Build and run

  1. Generate: python scripts/model_generation.py --variant 3Dheart --model-type cpp (CVS_ANS_collab).
  2. Configure: cmake -S generated_models/3C_ANS_3Dheart -B generated_models/3C_ANS_3Dheart/build -DSUNDIALS_DIR=$HOME/software/sundials-7.1.1.
  3. Build: cmake --build generated_models/3C_ANS_3Dheart/build. This gives main0d, libmodel0d.a, libcirculation_api.a and api_test_driver.
  4. Run standalone: build/main0d -tEnd 10 -outDir out/. The chamber pressures stay at their placeholder values.
  5. Test the api: python scripts/check_3Dheart_api.py replays the 0D heart's pressures through lifex::Circulation and compares the volumes.
  6. Use from lifex: build against libcirculation_api with -DCVS_WITH_LIFEX, so iheart::Chamber comes from lifex.
